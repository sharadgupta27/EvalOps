# Building a FastAPI Backend from a Contract with a Coding Agent

*Part 3 of "Building EvalOps". Concepts: layered architecture, async I/O, ORM and migrations, auth vs API keys, domain errors.*

---

With the contract written, the backend's job is clear: implement exactly that, and keep it
that way. This post explains the structure the agent was asked to follow, and why each rule
exists.

## Concept 1: layers, and why agents need them more than humans

```text
app/api/routes.py      HTTP only: parse request → call one service method → return
app/services/          business logic (no FastAPI imports)
app/repositories/      ALL database access (SQLAlchemy queries)
app/models/            ORM tables        app/schemas/   Pydantic request/response models
app/llm/               the only code allowed to talk to an LLM provider
app/evaluators/        one module per evaluator type
app/worker/            background job processing
```

Why so strict? Because an agent completes the pattern it sees. If one route runs a SQL query
inline, the next twenty will too. Clear layers give the agent an obvious place for
everything, and make review easy: *does this router do anything but call a service?*

A route really is this thin:

```python
@router.post("/projects/{project_id}/runs", status_code=202, operation_id="createRun")
async def create_run(project_id: int, body: RunCreate, p: PrincipalDep,
                     repo: RepoDep, settings: SettingsDep) -> EvalRun:
    return await RunService(repo, settings).create(p, project_id, body)
```

Services raise **domain exceptions** (`NotFound`, `Conflict`, `Invalid`…) that know their HTTP
status; one exception handler converts them to responses. Services never import FastAPI, so
they're reusable from the worker, the seed script and tests.

## Concept 2: async, and why it matters for LLM apps

An eval run makes dozens of model calls, each taking seconds. The CPU is idle the whole
time: the process is just *waiting on the network*. Async Python lets one process wait on many
calls at once. So the endpoints are `async def`, the database uses SQLAlchemy's
`AsyncSession`, and the worker evaluates cases concurrently.

One gotcha: async SQLAlchemy can't lazily load relationships (there's no hidden I/O
allowed). So the ORM models have no relationships at all, and repositories query exactly what
they need. That's less magic, but more predictable.

## Concept 3: one database URL, many environments

```python
class Settings(BaseSettings):
    database_url: str = "sqlite+aiosqlite:///./evalops.db"
```

- **Unit tests:** a fresh SQLite file per test (fast, zero setup).
- **Docker / production:** `postgresql+psycopg://…`.
- **Integration tests:** a real Postgres in a throwaway container (Part 6).

`app/config.py` is the *only* module allowed to read environment variables. Settings are
validated at startup: in production the app **refuses to start** with the default JWT secret
or weak password hashing. A misconfiguration fails loudly on deploy instead of quietly in prod.

**Migrations.** Tables are created by Alembic migrations, never by the app. The first
migration was autogenerated from the models, then tested with `upgrade` and `downgrade` on
both SQLite and Postgres. Rule for agents: never edit a migration that may already have been
applied; write a new one. (In Part 9 a hook enforces this.)

## Concept 4: humans and machines get different credentials

| | Humans | Machines (CI, MCP, agents) |
|---|---|---|
| Credential | email + password → short-lived **JWT** | **project API key** |
| Scope | all their projects | exactly one project |
| Can manage project, keys, datasets | yes | no (403) |
| Can read results, start runs, call the gate | yes | yes |

API keys are 256 random bits, shown **once**, stored only as a SHA-256 hash (like a
password: if the database leaks, the keys don't), and revocable. Every request resolves to a
`Principal`, and every service method checks access through one function:

```python
async def project_for(self, principal: Principal, project_id: int) -> ProjectRow:
    """Return the project if the caller may see it. 404 (not 403) hides existence."""
```

Returning 404 instead of 403 for someone else's project avoids confirming that it exists.

## Concept 5: let the agent run things, and learn from what breaks

The most valuable thing the agent did in this phase wasn't writing code. It **ran** the code
and fixed what broke. Real examples from the log:

- A service method named `list` shadowed Python's builtin `list` *inside the class body*, so a
  later annotation `-> list[ApiKey]` crashed at import. Renamed to `list_all`.
- A test helper used `cases or default_cases()`, so passing an empty list (`[]` is falsy)
  silently created 5 cases. Classic Python bug, caught by a failing assertion.
- On Windows, the async Postgres driver can't run on Windows' default event loop. The fix was
  a tiny `run_async` helper that picks a compatible loop.
- The unit suite took 38 s against a budget of 30 s. The cause was bcrypt at 12 rounds on every
  test login. Rounds became a setting: 4 in tests, and the app refuses less than 12 in prod.

None of these would show up from reading code. All of them show up from running tests.

## CSV/JSONL import: errors per row, not per file

Bulk import is where products feel polished or painful. EvalOps imports valid rows and
reports invalid ones with their row number:

```json
{"imported": 2, "errors": [{"row": 2, "message": "all input columns are empty"}]}
```

In a CSV, `expected_output` and `tags` are special columns and every other column becomes a
template variable. Uploads are capped at 2 MB, and (after the security review in Part 11)
oversized bodies are rejected *before* they're parsed.
